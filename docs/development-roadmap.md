# 开发路线与验收

本路线实施 [架构设计](../ARCHITECTURE.md) 和 [运行时契约](runtime-contracts.md)。所有阶段初始状态均为“计划”，完成条件以实际验证记录为准。

## 1. 开发顺序

```text
P0 技术原型与契约裁定
 → P1 三项目与整体构建
 → P2 宿主及基础管理闭环
 → P3 TML 内容与协议适配
 → P4 旧插件兼容范围
 → P5 可分发版本验收

P3 完成后可独立研究：
S1 模组 SSC 可行性 → S2 持久化与同步 → S3 明确范围的 SSC 发布
```

基础管理版本必须经过 P3 和 P5。不能因为 TShock 启动成功就跳过模组网络和内容回归。P4 可以先交付有限的已验证插件集合；SSC 不阻塞基础管理版本。

## 2. P0：技术原型与契约裁定

### 工作项

- 记录当前 TML 精确版本、.NET 目标及 TShock 上游基线。
- 使用最小 API/TShock 替身和一个插件验证三程序集依赖。
- 验证 TML 库打包后是否改变程序集身份、引用或加载位置。
- 验证 Mod.Load 之前直接引用的核心由谁解析，缺失核心时 TML 的诊断是否足以定位。
- 记录 TML、API、TShock、样例插件的 AssemblyLoadContext。
- 验证样例插件中的 TShock/API 类型与宿主对象可直接交互。
- 验证 SQLite 等首期必要的原生依赖定位。
- 为 TML 服务端生命周期记录顺序、线程、次数及世界状态。
- 对照 TSAPI 基线确认 GameInitialize/GamePostInitialize 的语义。
- 验证正常退出、初始化失败、同进程 Mod 重新加载的行为。
- 验证 TML 网络插入点：能放行扩展协议，同时在原版操作生效前取消。

### 必须形成的决策

| 问题 | 优先方案 | 通过证据 |
|---|---|---|
| 核心如何交付 | TML 内置库打包 | 干净安装只放发行物即可启动 |
| 第三方在哪个上下文加载 | 复用核心共享身份的统一加载策略 | 类型相等、依赖解析唯一 |
| 插件初始化在哪个阶段 | 内容和 API 所需条件满足的最早位置 | 生命周期轨迹及样例断言 |
| 世界事件如何映射 | 满足选定 TSAPI 语义的 TML 回调 | 首次加载及再次加载次数正确 |
| 同进程重新加载 | 先确认 TML 实际行为 | 无旧插件实例、旧 Hook 残留；或明确阻止并要求重启 |
| 网络在哪一层拦截 | 保留 TML 协议所有权且支持前置取消 | 普通包和模组包行为均正确 |
| 原生库如何定位 | 固定发行布局下的按平台解析 | 空目录安装的数据库读写成功 |

### 验收

- [ ] 重复运行原型得到一致的事件顺序和身份结果。
- [ ] 样例插件从自身引用读取 TShock 状态，并可向宿主 API 注册事件。
- [ ] 核心 DLL 重复、缺失和版本冲突均有可定位失败。
- [ ] 取消测试包后对应游戏操作没有发生。
- [ ] 模组握手和样例 ModPacket 到达其 TML 接收者。
- [ ] 原型结论已回填文档，选定一个实际发布布局和加载策略。

完成 P0 前，避免批量搬运所有旧 Hook 或扩展 SSC 数据库。

## 3. P1：项目拆分与构建

### 文件职责迁移

| 当前位置 | 目标 |
|---|---|
| src/TShockLoader/TerrariaApi.Server | src/TerrariaApi.Server |
| src/TShockLoader/OTAPI 中公开兼容类型 | API 的 Compatibility/OTAPI 模块 |
| OTAPI 中直接调用 On Hook 的实现 | 拆出平台依赖实现，归宿主 HookBridge |
| src/TShockLoader/Terraria/ITile.cs | 根据兼容能力裁定保留表面或明确不支持；不视为 Tile 适配已完成 |
| src/TShockLoader/HookAttach 及 Hooking 中底层安装代码 | 宿主 HookBridge |
| src/TShockLoader/Host | 宿主 Runtime |
| src/TShockLoader/Relinker | 宿主 Compatibility |
| TShockAPI 对 Loader 的 ProjectReference | 改为对 API 的引用 |
| TShockAPI 的 AfterBuild 部署动作 | 显式打包/本地部署步骤 |

路径是职责映射，不要求机械移动整个文件。例如现有 HookManager 同时包含事件契约和平台行为时，先按职责拆开。

### 构建约定

- TML 安装/引用路径通过可配置 MSBuild 属性传入；构建环境缺失时直接提示。
- 目标框架由选定 TML 版本决定，不为追新单独升级到宿主不支持的运行时。
- 顶层构建产生三个项目产物和一个完整发行包。
- API → TShockAPI → Loader 的编译顺序由 ProjectReference 决定。
- 依赖锁定版本；现有二进制依赖记录来源和版本，适合包管理的依赖按需迁移。
- 构建与打包在工作区输出目录进行，部署到运行目录是独立显式动作。
- 输出引用程序集和一个 SDK 样例，说明第三方插件该引用哪些 DLL。
- 保留上游版权头，补齐仓库 LICENSE 和发行第三方 notices。

### 验收

- [ ] 干净环境可按文档完成构建，项目引用无环。
- [ ] TShockAPI/API 均不引用 Loader。
- [ ] 构建不会改变开发者正在运行的服务器目录。
- [ ] 发布包包含必需依赖，且核心不依靠 ServerPlugins 扫描发现。
- [ ] SDK 样例编译并在发行包环境运行。

## 4. P2：宿主与基础管理闭环

### 工作项

- 唯一宿主会话拥有启动、插件实例、事件桥接和关闭。
- TShock 显式创建一次，显示为 Core 来源。
- 先发现和构造，再按固定顺序初始化。
- 记录实际初始化顺序及部分构造资源，实现第三方逆序清理、TShock 最后释放。
- 明确插件 Priority 与初始化 Order 的不同语义。
- 所有 Hook 具有释放路径；反射 Detour 保存句柄。
- 核心配置、目录、日志和启动失败报告统一。
- 接入账号、认证、命令、权限和正常保存退出。
- 管理命令和 REST 的游戏状态操作遵循线程归属。

### 验收场景

| 场景 | 预期 |
|---|---|
| 无第三方插件启动 | TShock 管理命令可用，Core 恰好一份 |
| 一个 Order 为负的插件 | 能在 TShock.Initialize 前注册事件 |
| Order 相同的两个插件 | 多次启动排序一致 |
| Priority 不同/相同的订阅者 | 按约定优先级及注册顺序执行 |
| 插件构造失败 | 启动失败，已构造资源清理 |
| 插件 Initialize 中途失败 | 不报告 Ready；插件注册及底层 Hook 清理 |
| TShock 初始化失败 | 不进入可服务状态 |
| 正常停止 | 最终保存完成，第三方逆序释放、TShock 最后释放，REST/任务退出 |
| 负 Order 插件释放时访问 TShock | 已建立的 TShock 资源仍有效 |
| 世界切换后再 Stop | 同一世界的最终保存不重复，停止不访问已卸载世界 |
| 清理过程中再次抛错 | 其他资源仍清理，保留最初异常 |
| 切换数据根/当前工作目录 | 仍访问配置指定的同一数据根 |
| 两实例共用安装根 | 使用各自 InstanceRoot，数据库和插件互不污染 |

输出一次完整运行日志和失败注入测试结果。此阶段称为管理原型，完整可用版本仍需 P3。

## 5. P3：TML 内容、协议和世界行为

### 工作项

- 建立 Hook 支持矩阵，优先完成账号/权限和管理路径需要的事件。
- 对包格式、偏移、长度、未知包处理建立统一边界。
- 确保握手、ModNet、ModPacket 不被原版范围规则拦截。
- 全链路使用动态内容注册数据，包括命令查找、发包和反作弊。
- 审查原版速度/伤害/堆叠等规则，按模组能力调整。
- 世界加载、保存、卸载使用 P0 裁定的映射。
- Tile 类操作基于 TML 的实际存储语义适配。
- 写清区域保护已覆盖的操作和未验证的模组自定义操作。

### 最小真实多人回归

使用两个 TML 客户端和至少一个含模组物品、方块、自定义数据包的测试 Mod：

1. 首次连接、模组同步、认证、进入世界、断线重连。
2. 聊天和管理命令可用；无权限操作被正确拒绝。
3. 获得、丢弃、拾取模组物品，客户端显示及服务端状态一致。
4. 放置、破坏模组方块；允许区域可操作，受保护区域按已支持规则拒绝。
5. 样例 ModPacket 双向同步；测试合法的大 payload 和畸形包。
6. Hook 修改参数确实改变操作，Hook 取消确实阻止操作。
7. 世界保存并重启后，已测试的世界状态正确。
8. 更新事件的计数、调用线程和前后顺序符合契约。

畸形输入测试必须有超时，并在隔离测试实例中运行。每项记录服务端证据和客户端观察，不能仅以日志出现“玩家进入”认定交互通过。

## 6. P4：旧插件兼容

### 工作项

- 实现按已知源程序集和类型/成员映射的 Relinker。
- 普通依赖、核心共享依赖与兼容映射分别处理。
- 原始插件保持不变；先完成内存改写和诊断。
- 预检程序集/成员错误，并保留运行期异常定位信息。
- 先选择实际需要的命令、权限和事件插件，逐个建立回归。
- 发布 SDK 引用说明、兼容矩阵和典型迁移示例。

### 兼容矩阵记录格式

| 字段 | 记录要求 |
|---|---|
| 插件 | 名称、版本、源码或文件来源 |
| 文件 | 内容哈希，避免混淆同版本不同编译物 |
| 目标环境 | 产品版本、TML 版本、模组集合 |
| 模式 | 原生重编 / Relink / 需要源码适配 |
| 能力 | 已实际验证的命令、事件、数据操作 |
| 限制 | 不支持的成员、反射或底层行为 |
| 证据 | 验证日期、用例、结果与日志位置 |

### 验收

- [ ] 普通未映射 NuGet 依赖可以正常解析。
- [ ] 已知旧程序集引用映射到正确的共享程序集实例。
- [ ] 嵌套类型、泛型、字段和方法签名样例经过验证。
- [ ] 不支持的 Tile/ITile 或底层签名给出具体诊断。
- [ ] 同名依赖冲突与重复核心文件不会静默选择一份。
- [ ] 已宣布支持的插件完成实际使用路径，而非只有 Initialize 成功。
- [ ] 未验证插件在矩阵中明确标识。

## 7. P5：发布与可维护性

### 发布物

- 一个完整安装包，附精确支持版本。
- 核心组件、依赖库、插件 SDK 引用和最小样例。
- 安装、数据目录、插件安装、更新、诊断及数据备份说明。
- 版本清单：产品、API、TML、上游 TShock 基线、目标框架、支持平台。
- 已验证兼容矩阵及功能边界。
- 许可证和第三方 notices。

首个发布平台为当前 Windows x64 环境。Linux 等平台只有在相应构建、原生依赖和运行回归通过后才列入支持清单。

### 验收

- [ ] 从干净 TML Server 目录按文档安装并启动。
- [ ] 发行包内核心身份正确，无需手动补拷开发机 DLL。
- [ ] 使用真实发布产物执行 P2/P3 核心场景。
- [ ] 更新发行文件不会覆盖数据、日志或第三方插件。
- [ ] 数据格式变化时提供相应迁移与失败恢复说明。
- [ ] 启动日志能定位插件和依赖问题，且无凭据泄露。
- [ ] 有可重复执行且有超时的基础验证入口。

## 8. S1–S3：模组 SSC 专项

### S1：可行性

选择包含自定义物品数据、ModPlayer 状态和额外槽位的真实模组，逐项记录数据在服务端的可见性，以及保存、恢复、客户端同步所需入口。

必须通过“断开连接 → 服务器保存 → 完整重启 → 恢复 → 客户端观察”验证。若需客户端组件，确定其部署和协议后再进入 S2。

### S2：持久化

基于验证结果确定数据模式及 TML 序列化调用。覆盖稳定内容身份、模组版本信息、事务保存、缺失模组的数据保留、格式迁移和恢复。

数字 ID 变动、额外槽位、模组移除/恢复以及自定义物品数据，是必需回归项。数据恢复不能静默丢失未知字段或覆盖最后完整存档。

### S3：发布范围

只有端到端验证过的 SSC 能力可以开启。发布文档说明支持的模组/数据类型、是否需要客户端组件、升级与恢复要求。纯服务端基础管理版本继续保持独立可用。

## 9. 测试分层和完成定义

| 层级 | 适合验证 | 不代表 |
|---|---|---|
| 编译/引用检查 | 项目依赖和目标框架 | 程序集运行时身份正确 |
| 定向自动化测试 | 排序、注册、失败清理、Relinker 样例 | TML 客户端交互正常 |
| 服务器集成 | 生命周期、插件/依赖加载、保存退出 | 所有模组玩法兼容 |
| 真实多人验证 | 同步、权限、模组物品/方块行为 | 未测试模组自动获得支持 |
| 发行物验证 | 安装布局和依赖完整 | 其他操作系统同样可用 |

不为简单目录移动或文字调整编写镜像测试。优先覆盖可能造成重复初始化、数据损坏、协议中断和权限失效的契约。

每阶段完成记录必须包含：实际版本、执行命令或步骤、结果、关键日志/断言、已知限制、已更新的文档。发布和部署是独立动作；完成开发不自动意味着已发布。

## 10. 上游升级和设计评审

### 上游仓库

| 组件 | Fork | 跟踪分支 | 当前基线 |
|---|---|---|---|
| TShock | https://github.com/Megghy/tShockLoader.TShock | `general-devel` ← Pryaxis/TShock | `9508768863c2` (2026-09-09) |
| TSAPI | https://github.com/Megghy/tShockLoader.TSAPI | `general-devel` ← Pryaxis/TSAPI | `d4add121c246` (2026-09-02) |

TML 适配在各 fork 的 `tml` 分支（TShock 仅 `TShockAPI/`，TSAPI 仅 `TerrariaServerAPI/TerrariaApi.Server/`）。本仓用 subtree 接入：

```text
git subtree pull --prefix=src/TShockAPI tshock tml
git subtree pull --prefix=src/TerrariaApi.Server tsapi tml
```

跟上游：在 fork 上更新 `general-devel`，再 merge 进 `tml`，最后由本仓 subtree pull。不要直接 submodule 官方仓库。

当前运行时基线：tModLoader `1.4.4.9+2026.07.3.0`（`TML_2026_07`，net8.0）；TShock 产品版本 `5.2.3`；API 契约 `2.1`。

### 上游升级流程

1. 固定目标 TML/TShock 基线，记录源码版本与依赖变化。
2. 检查公开类型和成员、Hook 目标签名、网络格式、内容注册、序列化及原生依赖。
3. 在适配层修复差异，业务代码只处理属于自身的语义变化。
4. 运行受影响的契约用例，再执行核心集成和发行物回归。
5. 更新版本清单和兼容矩阵，通过后发布。

### 提交前评审问题

- 改动的状态由谁拥有，是否仍只有一份？
- 是否需要调整公开契约，已有插件如何验证？
- 初始化、失败及退出三条路径是否完整？
- 可取消 Hook 是否在副作用前执行，参数是否真正回写？
- 动态内容与跨重启数据是否使用正确标识？
- 是否新增了无实际需求的框架、配置项或隔离机制？
- 构建、运行与发布的验证结论是否分开记录？
- 待验证假设是否明确，下一步实验是否能裁定它？

## 11. 当前原型的使用说明

当前源码已拆成三个项目，依赖方向为 API ← TShockAPI ← Loader。TShock 由宿主显式构造，核心程序集不得出现在 ServerPlugins。构建不向正在运行的服务器目录复制文件。后续按 P0 验证结果固化打包与加载策略。

原型中的某段实现不构成兼容承诺；保留其行为应依据上游公开契约或实际插件需求。开发时仍先检查最新文件和本地改动，按模块迁移，避免覆盖无关工作。
