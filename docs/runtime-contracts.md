# 运行时与兼容契约

本文细化 [架构与设计方针](../ARCHITECTURE.md)。所有名称为目标设计，具体 TML 回调映射在原型通过后固化。

## 1. 会话状态与资源拥有权

宿主会话状态：

```text
Created → Preparing → Initializing → Active → Stopping → Stopped
               ↘             ↘         ↘
                 Faulted → Cleanup → Stopped
```

Active 表示插件系统已初始化。对外 Ready 还要求世界就绪、TShock 就绪以及进入服务阶段的条件全部满足。世界状态另行维护为 Unloaded / Loading / Ready / Unloading，避免将一个进程的会话状态与多次世界切换混合。

状态仅由宿主改变。重复进入 Startup 是生命周期错误，直接报告；重复调用 Stop 允许安全返回。初始化失败必须经过统一清理，不能依赖“启动成功”布尔值才执行释放。

| 资源 | 拥有者 | 释放时机 |
|---|---|---|
| TML Hook、RuntimeDetour | 宿主 HookBridge | 会话停止或安装中途失败 |
| 程序集解析回调 | 插件加载器 | 插件全部释放后 |
| TSAPI 插件注册 | API 注册集合，记录插件拥有者 | 插件释放后由宿主清除残留 |
| TShock 数据库、REST、定时任务 | TShock 实例内部 | 全部第三方释放后的 TShock.Dispose |
| 第三方插件资源 | 对应插件 | 插件.Dispose |
| 宿主日志和启动诊断 | 宿主 | 其余清理完成后 |
| 世界相关临时状态 | 对应世界会话 | 世界卸载 |

资源取得成功后立即登记清理动作。清理按依赖的逆序进行，其中 TShock 作为基础资源在全部第三方之后释放；错误处理是退出边界，可以收集多个释放异常并继续清理，最后保留原始失败及清理失败记录。禁止用清理异常替换最初的启动异常。

首次版本不提供插件热更新。正常进程退出必须释放资源；TML 是否会在同进程重新加载服务端 Mod，以及加载上下文能否支持这种行为，在 P0 验证。若无法可靠支持，必须明确要求完整重启并在重新启动插件系统前失败，避免复用旧状态。

## 2. 启动阶段

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| Prepare | 解析绝对目录、验证版本组合与核心身份 | 核心可用且只有一份 |
| Bind | 建立共享程序集解析、API 会话和 Hook 桥接 | 日志/事件注册可用 |
| Discover | 索引第三方文件和依赖，读取元数据 | 重复、冲突、禁用规则已处理 |
| Construct | 显式构造 TShock，再构造第三方插件 | 每个插件恰好一个实例 |
| Initialize | 按兼容排序初始化全部实例 | 成功初始化顺序已记录 |
| Activate | 对接 TML 世界/服务阶段 | 发出对应就绪事件并报告状态 |

表中 Prepare 开始前，TML/CLR 可能已经装载核心程序集。Bootstrap 属于 TML 的库装载阶段，必须由发布布局和声明依赖保证成功。Bind 复用这些已有核心实例，并建立第三方解析策略，不再从磁盘装载第二份核心。入口执行前的失败使用 TML 自身诊断，打包验证必须覆盖该路径。

这是一份逻辑阶段划分，不要求全部工作发生在 `Mod.Load` 同一次调用中。TML 内容何时注册完成、世界何时加载，都要由宿主回调驱动。

构造函数仅建立对象和已有契约要求的基础状态。数据库连接、REST 启动、任务调度和游戏操作放在约定的初始化阶段。旧插件构造期要求的状态应通过样例明确；无法支持时给出插件适配要求。

### 2.1 排序与 TShock 初始化

- TShock 首先被构造，其程序集和构造期基础状态可供插件引用。
- 所有插件实例包含 TShock，按 `Order` 升序、`Name` 使用明确的 Ordinal 比较排序。
- 同值再按类型全名和程序集身份排序，结果不依赖文件枚举顺序。
- 保留负 Order 插件在 TShock.Initialize 前注册事件的能力。
- TShock 核心 Ready 只在 TShock.Initialize 成功完成后成立。
- 使用数据库、账号管理器等资源的插件必须处在 TShock 初始化之后，或订阅已定义的 TShock 初始化事件。
- 不将 Order 演化成隐含依赖解析器；初期不新增通用插件依赖图。

事件回调的 Priority 与插件 Initialize 的 Order 是不同契约。保持现有事件注册“Priority 高者先执行、相同值按注册顺序”的语义，编写独立回归样例。

### 2.2 事件阶段

| 事件/概念 | 契约 | 映射准则 |
|---|---|---|
| GameInitialize | 兼容 API 初始化阶段，一次/会话 | 所有需要接收者已注册；回调不再次启动宿主 |
| TShock.Initialized | TShock 初始化完成，一次/实例 | 保持既有公开事件语义 |
| GamePostInitialize | 按选定 TSAPI 基线确认其原有含义 | 不能仅凭名称映射为任意 Post 回调 |
| 内容可用 | 所需动态注册表已完成 | 用于依赖 ItemLoader 等注册结果的工作 |
| 世界就绪 | 世界及模组世界数据可用，一次/世界加载 | 与进程初始化分离 |
| 更新前/后 | 约定游戏更新位置的一对事件 | 检查服务器是否实际经过该回调 |
| 世界卸载 | 确认最终保存阶段已完成并清理世界状态 | 卸载通知本身不保证仍能保存 |
| 停止 | 终止接入和任务，完成保存后释放 | 不由第三方事件反向触发第二次初始化 |

TML 的 ModSystem 提供世界和更新等生命周期入口；其中 PostWorldLoad 描述的是模组世界数据已加载后的阶段。具体版本中可用的入口和 TSAPI 对应关系仍需记录运行轨迹验证。[官方 ModSystem 文档](https://docs.tmodloader.net/docs/stable/class_mod_system.html)

GamePostInitialize 的调用次数、相对世界加载的位置，以及现有 TShock.OnPostInit 的需求，属于 P0 必须裁定的契约。如果引入内部 WorldReady 事件，它只服务宿主内部，不自动扩大插件公共 API。

## 3. 停止与部分失败

正常停止顺序：

1. 进入 Stopping，协调 TML 停止新接入，取消宿主新增工作。
2. 通过下述世界保存协调规则完成必要保存，并等待受控任务结束。
3. 按实际成功初始化顺序逆序释放第三方插件；释放期间保留 TShock、API、解析器和日志。
4. 清理已构造但未成功初始化的第三方对象，随后释放 TShock 及其部分初始化资源。
5. 清除 API 中的插件事件注册和会话引用。
6. 解除底层 Hook、RuntimeDetour 和程序集解析回调。
7. 释放剩余宿主资源，进入 Stopped。

沿用 TerrariaPlugin.Dispose 作为公开释放契约；PluginContainer 的内部状态清理不意味着自动新增一个插件 DeInitialize 虚方法。

初始化失败对象可能已经登记事件或打开资源，必须纳入部分初始化清理。容器记录 Constructed / Initialized / Disposed 等必要事实即可，不建立复杂工作流框架。

负 Order 插件在释放时仍可使用已成功建立的 TShock 资源，因此 TShock 固定最后释放。任意第三方之间未声明的释放依赖不由宿主推断；插件应遵循其初始化顺序对应的逆序释放契约。

### 3.1 世界保存协调

世界文件和模组世界数据由 TML 的保存流程拥有。宿主只在确认支持的保存/停止入口请求该流程，并在游戏状态仍可用时完成相关业务数据保存；不另写一套世界序列化。

每次世界加载创建一个递增的世界会话标识，记录该会话最终保存是否已请求、是否完成。正常退出和宿主 Stop 汇入同一个协调入口：已有保存任务时等待该任务，已完成时不重复请求，失败时报告失败而非标记完成。正常周期保存不使用这个最终保存标志。

世界卸载通知只负责核对并结束世界会话，不假设通知时仍可保存。Stop 发现世界已卸载时不访问旧世界；插件 Dispose 也不得依赖已卸载世界。所需游戏数据应在适当的保存阶段取得。P0 必须确认正常退出/世界切换的保存先于卸载，异常终止只保留已有成功存档，不承诺退出保存。

## 4. 程序集加载

### 4.1 身份规则

共享列表至少包括 TML、FNA、TerrariaApi.Server、TShockAPI，以及公开签名中使用、必须统一身份的依赖。第三方插件请求这些程序集时返回宿主的已有实例。

加载器使用程序集元数据身份索引，而非只使用文件名。发现相同 simple name 的不同文件，必须进行身份/内容比较；冲突直接失败，不能让文件枚举顺序决定加载结果。名字相同且版本相同也不代表二进制内容相同。

.NET 的 AssemblyLoadContext 对程序集解析和类型身份有明确约束。上下文内只能装载一个 simple name 对应的版本；跨上下文共享必须返回同一程序集实例。[官方说明](https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext)

目标策略是一个统一管理的插件程序集集合。P0 选择与 TML 兼容的具体加载上下文归属；无需为每个插件创建独立隔离环境。此加载器不构成安全沙箱。

首期采用全局单版本依赖闭包：同一解析域内的普通依赖也不能同时保留多个同名版本。依赖冲突时输出冲突文件、版本和请求者，要求插件选择一致依赖或重新编译；“正常解析 NuGet 依赖”只指按该策略解析，不包含私有多版本隔离。

### 4.2 第三方发现

- 首期支持 ServerPlugins 顶层托管 `.dll` 和既有 `.dll-plugin` 入口形式。
- 依赖库与插件入口通过程序集元数据区分；普通依赖没有 TerrariaPlugin 子类，不创建容器。
- 原生库通过原生加载路径处理，不交给 Relinker；文件被识别为原生库不意味着吞掉其他加载错误。
- 先建立文件索引，再加载/发现类型，避免类型解析依赖于目录遍历顺序。
- 一个程序集可提供多个公开、非抽象插件类型；各自校验 API 属性和构造签名。
- ignoredplugins.txt 按稳定文件标识匹配，去掉空白和空行；行为写入用户文档。
- 忽略规则阻止插件入口实例化，不承诺其程序集不会作为其他插件依赖被解析。
- 核心组件副本总是视为安装错误，不受忽略规则豁免。

首期启用插件加载失败或 API 不受支持时，整个启动失败。用户通过显式忽略有问题的插件重新启动，避免实际启用集合与预期不符。

插件依赖只从既定受控位置解析；不为每个版本失败轮流尝试大量目录。核心公开依赖版本冲突应指出双方来源。独立插件目录和私有版本隔离在有具体需求后再评估。

### 4.3 Relinker 流程

```text
读取 PE 元数据
→ 检查原始程序集引用
→ 匹配已知源程序集和类型/成员
→ 必要时改写
→ 检查改写后引用与目标成员
→ 交给统一加载器
```

约束：

- 只重写已知来源的引用，不能仅按命名空间前缀改写任意第三方类型。
- 普通 .NET/NuGet 依赖按正常策略解析；“无需映射”不同于“无法解析”。
- 一个旧程序集可能同时包含游戏类型与 OTAPI 类型，需要按类型实际归属拆分目标。
- 对支持的 OTAPI 类型，将 TypeRef 的程序集作用域改为 TerrariaApi.Server，并验证 MemberRef 所属类型及其签名；嵌套类型需沿声明类型正确解析作用域。残余 AssemblyRef 的保留或移除以真实引用为准，不用全程序集别名替代类型检查。
- 对嵌套类型、泛型签名、字段/方法签名和目标成员变化建立样例。
- Tile/ITile 的类、结构体、字段、属性和存储语义差异必须单独处理；声明一个同名接口不会使 TML Tile 自动实现它。
- 涉及反射字符串、动态生成 IL、运行时 Detour、强名称身份的插件，需要专门适配或明确列为不支持。
- 元数据预检查只能发现一部分错误；不能据此承诺所有延迟 JIT 路径正确。
- 原始插件文件保持不变；首期内存改写。实测启动成本需要时才增加磁盘缓存。
- 缓存键必须包括插件内容哈希、兼容规则版本、目标程序集版本/内容以及相关依赖变化，不能只看文件修改时间。

## 5. Hook 桥接

每个支持的 Hook 在支持矩阵中记录：

| 字段 | 内容 |
|---|---|
| 来源 | TML 公开 Hook、On Hook 或明确方法签名 |
| 目标 | TSAPI/OTAPI 事件 |
| 时机 | 原操作前/后；世界与玩家状态前置条件 |
| 线程 | 主线程、网络线程或其他已知来源 |
| 参数 | 哪些可修改，如何回写，如何影响原操作 |
| 取消 | Handled/Cancel 的含义、后续订阅者是否仍接收 |
| 拥有者 | 安装者、释放句柄、停止时机 |
| 验收 | 无订阅者、只读订阅者、修改者、取消者样例 |

一个底层操作只能有一个事件转发路径。TSAPI 与 OTAPI 兼容层如果需要共用，定义固定调用顺序，不允许两处 Hook 令同一事件重复触发。

没有订阅者时必须保持原操作行为。取消和参数改写必须真正到达 TML 原操作；不能只修改 EventArgs 而丢弃回写。

事件分发中的快照行为、Priority 和 Handled 传播按选定兼容基线实现。运行期插件回调异常在边界记录插件及 Hook 身份后向顶层错误策略传播；取消性操作失败不得默认放行。宿主故障如何安全停止服务需通过集成测试确认。

## 6. 网络和线程

### 6.1 数据包分类

1. 包框架边界校验缓冲区范围、长度和最小头部。
2. TML 专属握手、ModNet 和 ModPacket 交由 TML 正常处理路径负责。
3. 已支持的 Terraria 包在产生游戏副作用前经过 TSAPI/TShock 对应校验。
4. 未支持的包由选定 TML 版本的协议路径决定处理方式，并记录能力缺口。

“交由 TML”指保留其所有权，不是先执行全部游戏副作用再触发可取消事件。最终 Hook 插入位置必须同时满足 TML 的协议处理和 TShock 的前置取消要求。

不能用原版 PacketTypes 枚举范围或统一的历史长度上限截断 TML 扩展包。长度限制按真实包格式、传输边界和方向设置。读取偏移及 payload 长度只有一套约定，所有转接处用样例校验。

玩家连接、认证、内容同步、进入世界是不同阶段；账号和权限状态由 TShock 提供，协议握手由 TML 提供。同步途中不能重复创建玩家对象或提前认为玩家已进入世界。

### 6.2 线程归属

游戏对象读写优先在 TML 游戏线程完成。数据库、HTTP 和文件操作可以异步执行，但恢复到游戏状态修改时必须经过宿主明确的主线程调度入口。

保持既有同步 Hook 签名；需要立即决定是否取消的 Hook 不能改成 fire-and-forget。已有网络线程事件的线程语义先记录，迁移到主线程可能改变时序，必须单独验证。

后台任务由拥有者跟踪，使用取消令牌和有限等待；不使用 async void、未跟踪 Task 或延时轮询等待初始化。耗时诊断先度量，初期不自行构建响应式任务系统。

## 7. 动态内容与管理行为

运行期合法 ID 以 TML 注册表和相应 Loader 数量为准，例如 ItemLoader.ItemCount、TileLoader.TileCount。内容加载完成前不建立最终容量缓存。

原版反作弊中的速度、伤害、堆叠、射程等规则需逐项区分：

- 结构有效性和协议一致性：仍需验证。
- 账号、权限、区域规则：保留产品约束。
- 原版游戏平衡假设：需要适配模组内容，未验证规则不能直接惩罚合法模组行为。

仅提高 ID 上限不等于适配完成；发包/解包、查找内容、给予物品、区域修改和回滚都需覆盖模组内容。区域保护的首期支持范围按实际操作列出，不能宣称拦截所有模组自定义改图逻辑。

进程内使用动态 ID；跨进程持久化使用稳定内容标识或 TML 提供的序列化格式。重启后不假设同一个数字代表同一个模组内容。

## 8. SSC 与持久化

### 8.1 首期能力

基础管理版本关闭 SSC。用户尝试启用未实现的 SSC 时明确报错并说明当前能力，避免只保存部分状态却显示完整保护。

| 数据 | 完整 SSC 必须解决的内容 |
|---|---|
| 原版角色字段 | 基础属性、库存、装备、银行等既有字段 |
| 模组物品 | 稳定内容身份、ModItem 与 GlobalItem 自定义数据 |
| 角色扩展 | ModPlayer 状态、额外槽位及其所属模组 |
| 跨重启 | 模组集合和版本变化，动态 ID 重新分配 |
| 缺失模组 | 保留原始数据和明确恢复状态 |
| 同步 | 服务端保存的权威状态如何传递给客户端 |

优先研究 TML 的 ItemIO/TagCompound 等序列化能力。ItemIO 提供物品保存与加载入口；使用它仍需验证服务器是否拥有完整数据，以及整个角色状态是否覆盖。[官方 ItemIO 文档](https://docs.tmodloader.net/docs/stable/class_item_i_o.html)

纯服务端不能假定可读取所有客户端专属 ModPlayer 数据。完整 SSC 的原型应选择真实模组验证：如果需要客户端组件，另行定义配套 Mod 和协议，其版本检查属于该功能的必需条件。

### 8.2 数据模型原则

- 每份持久化记录包含 schemaVersion、稳定玩家/账号身份、世界或服务器作用域。
- 模组快照记录必要的模组名称及版本信息；具体表结构在原型证明数据可恢复后确定。
- 物品和扩展数据使用受支持的序列化格式，避免复制一套自定义二进制规范。
- 保存具有事务边界；失败保留最后一次完整记录。
- 缺失模组或未知格式时保留原始 payload，不静默转为空物品。
- 数据迁移有版本、备份/恢复路径和失败诊断；未知的新格式拒绝破坏性覆盖。
- 传输时间使用 Unix 毫秒时间戳并在字段名中标明单位；人类日志使用带时区的可读时间。
- 恢复数据后的客户端同步必须纳入测试，数据库写入成功不是 SSC 验收。

TShock 既有数据库模式保留其兼容需求。新数据存储先满足现有 SQLite 路径，再对实际提供支持的其他数据库运行同一组验证。

## 9. 诊断和版本信息

启动输出应包含产品版本、TML 版本、上游 TShock 基线、API 契约、实际目录、核心程序集身份，以及每个插件的来源/版本/兼容模式/初始化耗时。

失败输出至少包含阶段、插件类型、文件路径、缺失成员或冲突程序集、原始异常链和处理建议。不得输出凭据、完整数据库连接字符串或认证 Token。

宿主负责进程级诊断；TShock 保留业务日志接口。必要的桥接只建立一次，防止同一错误重复打印或循环转发。诊断列表可显示 Prepared / Active / WorldReady 等状态，最终 Ready 必须与真实运行状态一致。

核心 DLL 及插件依赖的原生库按平台/架构部署，通过明确路径解析。每个发布平台分别验收，Windows 启动成功不代表 Linux 的 SQLite 等原生依赖可用。
